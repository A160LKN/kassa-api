# Тест-стратегия «Кассы»

## Цель

Убедиться, что продажа билетов не ошибается с деньгами и местами: одно место не продаётся дважды, деньги не списываются дважды, оплата после истечения брони возвращается покупателю, а поддельный вебхук ничего не меняет. Это предметная область, где ошибка стоит денег, поэтому больше всего проверок — на одновременных запросах, повторах и переходах статусов заказа.

## Анализ рисков

| Риск                                                                        | Вероятность | Влияние | Как снижаем                                                                                                        |
| --------------------------------------------------------------------------- | ----------- | ------- | ------------------------------------------------------------------------------------------------------------------ |
| Одно место продано двоим                                                    | средняя     | высокое | атомарный `UPDATE … WHERE место свободно`; тест «50 покупателей на одно место»; ограничение `CHECK` в базе         |
| Двойное списание при повторе запроса (обрыв сети, двойной клик)             | средняя     | высокое | Idempotency-Key на заказ и оплату; тест «10 одновременных запросов с одним ключом — один заказ»                    |
| Вебхук обработан дважды                                                     | средняя     | высокое | таблица обработанных вебхуков; тест «5 одинаковых вебхуков одновременно — одна оплата»                             |
| Поддельный или старый вебхук меняет заказ                                   | низкая      | высокое | HMAC-подпись с отметкой времени; юнит-тесты на подмену тела, чужой секрет, повтор через 10 минут; API-тест — `400` |
| Оплата пришла после истечения брони — места проданы другому, деньги списаны | средняя     | высокое | поздняя оплата не продаёт места и запускает возврат; отдельный API-тест                                            |
| Недопустимый переход статуса (возврат без оплаты, оплата отменённого)       | низкая      | высокое | конечный автомат; все 25 пар «статус × действие»; fast-check на 2000 случайных последовательностях                 |
| Брони и заказы не освобождаются по истечении                                | средняя     | среднее | фоновая уборка; интеграционные тесты: истёкшее освобождается, живое — нет                                          |
| Отмена события оставляет оплаченные заказы без возврата                     | низкая      | высокое | API-тест: оплаченные возвращаются, неоплаченные отменяются, брони снимаются                                        |
| Перебор паролей                                                             | средняя     | среднее | лимит попыток; тест — шестая попытка за минуту получает `429`                                                      |
| Чужой заказ или событие доступны                                            | низкая      | высокое | API-тесты прав; чужое — `404`, а не `403`                                                                          |
| Ошибка вместо понятного ответа на мусорный ввод                             | средняя     | низкое  | битый JSON — `400`, id вне диапазона — `422`; ответы в одном формате с `X-Request-Id`                              |
| Схема базы расходится с миграциями                                          | низкая      | среднее | CI генерирует миграцию заново и падает, если появилась разница                                                     |

## Уровни тестирования

| Уровень            | Что проверяем                                                                                                         | Инструмент                                       | Сейчас        |
| ------------------ | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ------------- |
| Статический анализ | типы, линтер, форматирование, совпадение миграций со схемой                                                           | TypeScript strict, ESLint, Prettier, drizzle-kit | весь код      |
| Юнит               | конечный автомат заказа, пароли, JWT, подпись вебхука, курсор, настройки                                              | Vitest, fast-check                               | 27            |
| Интеграционные     | одновременные запросы на настоящем PostgreSQL, уборка, ограничения базы                                               | Vitest, PostgreSQL                               | 8             |
| API                | контракт HTTP: вход, события, бронь, заказы, оплата, вебхуки, отмена события; настоящий HTTP-вебхук от учебного шлюза | Vitest, `app.inject`                             | 57            |
| Смоук в Docker     | собранный образ: вход → бронь → заказ → оплата → вебхук → `paid`                                                      | `scripts/smoke.sh` в GitHub Actions              | каждый прогон |
| Ручное             | документация API, живой сервер, сценарии через Swagger                                                                | [чек-листы](checklists.md)                       | перед релизом |

Почему так много интеграционных проверок на гонки: юнит-тест не поймает двойную продажу — её создаёт база, когда два запроса приходят одновременно. Поэтому такие тесты запускают десятки параллельных запросов на настоящем PostgreSQL и проверяют итог в базе.

## Окружения

| Окружение                              | Назначение                                              |
| -------------------------------------- | ------------------------------------------------------- |
| Локально: Docker Compose (PostgreSQL)  | разработка и отладка тестов                             |
| GitHub Actions: Ubuntu, PostgreSQL 17  | автоматический прогон на каждое изменение               |
| GitHub Actions: собранный Docker-образ | смоук всего сценария покупки                            |
| Render + Neon                          | живой сервер с документацией: ручной смоук после деплоя |

## Тестовые данные

- Перед каждым тестом таблицы очищаются (`TRUNCATE … RESTART IDENTITY CASCADE`): тесты независимы.
- Пользователи, события и залы создаются хелперами через API, а не прямой записью в базу: так тест проходит тот же путь, что и клиент.
- Учебный платёжный шлюз: `tok_success` — оплата пройдёт, `tok_declined` — отказ банка. Шлюз шлёт настоящий подписанный вебхук.
- Демо-данные (`SEED_DEMO=true`): два события с залами, организатор и покупатель — для ручной проверки.

## Критерии

**Начало тестирования:** сборка проходит типы и линтер, миграции применяются.

**Готовность к релизу:**

- все автотесты зелёные, покрытие строк не ниже 90 %;
- смоук в Docker прошёл;
- ручной смоук на живом сервере пройден;
- нет открытых дефектов Critical и Major; найденные оформлены в [Issues](https://github.com/A160LKN/kassa-api/issues?q=is%3Aissue) и закрыты тестом.

## Дефекты

| Критичность | Определение                                                 | Пример                                       |
| ----------- | ----------------------------------------------------------- | -------------------------------------------- |
| Critical    | деньги или места: двойное списание, двойная продажа, утечка | одно место досталось двум покупателям        |
| Major       | функция не работает, обходного пути нет                     | в афише у каждого события «свободно 1 место» |
| Minor       | работает с ошибкой, которая не влияет на деньги             | неточный текст ошибки                        |
| Trivial     | косметика                                                   | опечатка в описании в Swagger                |

## Что не тестируется

- Настоящий платёжный провайдер — вместо него учебный шлюз с тем же протоколом (подпись, повторы, задержки).
- Нагрузка на тысячи покупателей — бесплатный хостинг. Корректность при одновременных запросах проверена интеграционными тестами.
- Фронтенд — проект только API.
